# 90 天验证计划
## 珊瑚哨兵 Reef Sentinel

**验证的核心问题只有一个**：这套 1 到 8 天的危险指数预报（数值天气预报驱动），是否真的改变了仙本那珊瑚相关从业者的决策，并且比他们现在凭经验判断更好？

> 时间范围：第 1 到 90 天（自提交日起）。不追求"完成科学验证"，只追求"用最小成本拿到能证伪的证据"。
> 对标基线：**从业者的现状判断**（凭天气 App、经验与现场感觉）+ 持续预报 + 气候平均。

---

## 一、成功标准（事先声明，避免事后编故事）

| 编号 | 指标 | 目标 | 测量方式 |
|---|---|---|---|
| S1 | 预报准确性（回测延伸） | 在验证期内新增数据上，模型 1 到 7 天 RMSE 仍低于持续预报与气候平均 | 每日自动记录预报值与实际值，90 天后一次性结算。落地方式：每次刷新由 tools/paper_forecast.py 写一份**带日期的冻结简报** `data/processed/archive/daily_brief_日期.txt` 并往**前向预报台账** `data/processed/archive/forecast_log.jsonl` 追加一行当日 8 天预报（risk / hi / half）；同一天重跑既不覆盖简报也不重复追加，保证事后不可修改。托管运行时由 `.github/workflows/daily_refresh.yml` 每天 06:10（马来西亚时间）自动执行；离线形态则每天双击 `更新数据.bat`。托管形态下 Actions 还会把成品页、`data/processed` 与原始记录 `data/raw` 一并提交回仓库（原始记录连续可查，而第二天的增量抓取只需补最近几天，不必重抓四年）。结算器 `tools/settle_forecast.py` 把台账与实际观测逐日对齐，按时效输出 RMSE、区间覆盖率与「上界达到高危险档而实际成灾」的命中率（S2），结果写 `data/processed/settlement_report.json`；自带 `--selftest` 用手算样例校验口径，现在跑会如实显示「暂无可结算记录」，因为最新一期的目标日还没被观测到。 |
| S2 | 校准度 | 预报 8 天内危险指数上界（hi）达到"高危险"档时，实际出现复合灾害的比例 ≥ 50% | 事件命中率统计 |
| S3 | 真实使用 | ≥ 2 家潜水运营商或 1 个修复团队，连续 4 周每周至少查看 1 次，并留下 1 条书面反馈 | 访问记录 + 每周 3 问题问卷。**先说清楚边界**：离线单文件形态没有服务器日志，这一项只能靠对方主动回报与我们的人工记录；只有上线到公开网址（或对方自己的服务器）后，访问记录才会自动留存。 |
| S4 | 决策影响 | 至少记录 3 次"因预报而改变计划"的具体事件（改期、提前巡检、暂停移栽、调整苗圃位置） | 事件日志（时间、原计划、依据、结果） |
| S5 | 信任与误报耐受 | 用户对误报的容忍门槛明确（例如"误报 3 次以内可接受"）；误报率被记录下来 | 访谈 + 日志 |
| S6 | 白化识别可信度（官方对照） | 与 NOAA 官方产品的年度排序一致（Spearman = 1.000），且同海域区域站点事件级命中 ≥ 10/13（当前 13/13），第二个独立官方站点（帕劳）复核 r = 0.921、p90 热日命中率 100.0% | 每次刷新由 pipeline/fetch_noaa_vs.py 自动拉取两个官方区域虚拟站点（沙巴 / 帕劳）的序列、再由 pipeline/bleaching_watch.py 重算年度相关系数、Spearman、全流域占比的事件级命中率、区域虚拟站点的事件级命中率与滞后天数，全部写进 data/processed/bleaching_watch.json，任何人可复算 |
| S7 | 学习型白化预警的增益 | 4 折扩展窗池化 PR-AUC 高于现行规则与基准发生率（当前 0.364 / 0.311 / 0.242） | pipeline/bleach_forecast.py 按扩展窗前推协议重跑（标准化、阈值与切点只来自训练段），分折结果与反例一并留在 data/processed/bleach_forecast.json；若验证期内增益消失，如实报告并回到规则口径 |

**证伪条件（若出现则如实报告并调整产品定位）**
- 90 天内 S1 不成立（新增数据上模型不再优于持续预报）；
- S3 不成立（无人持续使用）——说明需求判断有误，应把产品转向"科普与监测"而非"决策预警"；
- 用户反映误报频繁到影响信任（S5 崩），则提高触发门槛（改用 p95）以牺牲灵敏度换稳定性。

## 二、三阶段安排

### 阶段一：第 1 到 30 天 · 封闭验证与打磨（无外部依赖，可立即开始）

**目标**：在不动员任何人的前提下，先把"系统自己靠不靠得住"测清楚。

1. **前向纸面预报（paper forecast）**：脚本每天（或每周回补）自动生成未来 8 天预报（数值天气预报驱动）并存档为带日期的文件（`data/processed/archive/daily_brief_日期.txt`），同时把当天预报追加进台账 `data/processed/archive/forecast_log.jsonl`；同一天重跑不改写，冻结后不可修改；90 天后与实际观测结算。
2. **阈值敏感性分析**：把触发阈值从 p90 改为 p85 / p95，量化"漏报 vs 误报"的权衡曲线，输出给用户选择（而非由我们替他定）。
3. **接入官方数据（2026-10 已完成）**：在任何有公网的机器上执行 data/external/FETCH_NOAA_CRW.sh，取回 NOAA CRW 的 CRW_SST / CRW_SSTANOMALY / CRW_HOTSPOT / CRW_DHW / CRW_BAA（单点时间序列优先，体积小、当天可用）。取回后做一件事：**把 NOAA 的 DHW 与我们基于 Open-Meteo 的相对热压力指数并列画在同一张图上**，直接量化我们这套替代基线的偏差。这是本项目最诚实、也最有说服力的一步。**实际结果（2026-10）**：NOAA CRW 的单点 NetCDF 在本机不可达（ERDDAP 302 / 超时，环境里也没有 h5py、netCDF4、xarray），但换了两条同样官方的路子把数据拿到了 —— ① 全流域汇总 CSV `data/external/noaa_crw/stats_alert01_baa5.csv`（1985 年起 15,178 行）；② **同海域区域虚拟站点「Sabah, Malaysia」的纯文本逐日序列** `data/external/noaa_crw/vs_sabah_daily.csv`（1,474 行；抓取脚本 `tools/noaa_access_probe/fetch_vs_sabah.py` 可离线重跑，每日刷新链里则由 `pipeline/fetch_noaa_vs.py` 自动更新）。两条对照的结论与偏差量化见第七节。
4. **界面本地化**：英文界面 + 马来语关键词卡片（"Kapal / Stop" 类提示），保证潜店员工能看懂。

**产出**：前向预报存档、敏感性曲线、NOAA 对照图、双语界面。

### 阶段二：第 31 到 60 天 · 小范围真实使用

**目标**：让 2 到 3 个真人在真决策前看一眼。

1. **招募 2 到 3 家合作方**：优先仙本那本地潜店/度假村（通过沙巴公园管理局、当地潜店社群、以及马来西亚本地大学或 NGO 引荐），第 2 类对象是珊瑚修复志愿团队。
2. **交付方式**：一个手机号/WhatsApp 群 + 每日 1 条自动消息（今日档位 + 未来 3 天上界 + 一句行动建议）+ 离线 HTML 链接。**降低使用成本是采用率的第一决定因素。**
3. **每周 3 个问题的问卷**（不超过 1 分钟填完）：
   - 这周你看过几次预警？
   - 有没有因为预警改变过安排？（有 → 记录具体做了什么）
   - 有没有哪次你觉得系统明显说错了？
4. **访谈 1 次/家（20 分钟）**：他们真实的工作流是什么？决策在一天中的哪个时点做出？什么信息他们信不过？

**产出**：≥ 4 周的使用与反馈记录；≥ 3 条决策影响事件；至少 1 次明确的"系统说错了"事件（这正是最有价值的样本）。

### 阶段三：第 61 到 90 天 · 结算与公开

**目标**：把证据变成可传播、可复用的东西。

1. **结算 S1 到 S5**：把 90 天的前向预报与实际观测做一次完整结算（含失败案例）——前向预报的原始记录在 `data/processed/archive/forecast_log.jsonl`（每天追加、事后不可修改），跑 `python tools/settle_forecast.py` 即得到逐时效 RMSE、区间覆盖率与 S2 命中率。
2. **校准与改版**：按敏感性分析结果确定默认阈值；若 S2 未达标，明确写成"当前版本不应作为决策依赖，只作为参考"。
3. **成本与可持续性测算**：数据 API 成本（当前全部免费）、每周运维时间（目标 < 30 分钟/周）、潜在付费方与定价假设（潜店订阅 / 度假村 ESG 报告 / NGO 项目采购）。
4. **公开**：把脚本、数据、界面、结算报告与失败记录一起开源；写一篇面向从业者的中文与英文说明（不用学术腔）；向沙巴公园管理局与当地潜店社群提交一份一页纸建议。
5. **迁移验证（可选）**：把流水线换一个坐标（例如菲律宾图巴塔哈或印尼四王群岛）重跑，验证"方法可迁移"而不是"只对仙本那有效"。

## 四、风险与应对

| 风险 | 可能性 | 应对 |
|---|---|---|
| 找不到合作方（S3 失败） | 中高 | 备选路径：与沙巴本地大学/环保 NGO 合作作"教学与监测工具"；或退化为公众科普页面，仍可完成 S1、S2 的技术验证 |
| 官方数据取不回 | 中 | 已备好取数命令；即使取不回，也已披露替代基线的偏差风险，不影响方法完整性 |
| 验证期内无复合灾害事件（90 天可能一次都没有，按每年 12 到 15 天，90 天内期望约 3 天） | 中 | 同时结算**连续指数误差**而非只看二元命中；把无事件期本身作为"低风险期误报率"的测量 |
| 误报损害信任 | 中 | 阈值可调 + 明确显示不确定区间 + 不替用户做安全裁定 |
| 模型在新数据上失效 | 中 | 前向纸面预报机制本身就是监控器；一旦失效立即公开 |

## 五、伦理与安全边界（贯穿全程）

1. **不替代官方**：所有输出与材料均声明"非官方预警"，停航/闭园以 MetMalaysia 与沙巴公园管理局为准。
2. **不确定性与误判必须可见**：界面始终显示不确定区间与已知局限，不隐藏"模型在长时效上会退化"。
3. **不制造恐慌**：语言不用"珊瑚将死"这类断言，只描述压力等级与可行动作。
4. **数据最小化**：涉及合作方时只收集必要联系信息，不使用任何个人数据训练模型。
5. **顾及生计**：建议停航类内容明确标注"经济成本由使用者自行权衡"，避免让工具成为压价的借口。

## 六、90 天结束后我们希望知道的三件事

1. 预报**在什么时效上值得用户花时间看**？（我们目前已知道：分类形式只有 1 天有优势，回归形式 1 到 14 天都有）
2. **谁**真正会用它，用来改**什么**决定？
3. 如果换成 NOAA 官方海温产品，我们的相对指数会**偏多少**？**已答（2026-10）**：本站日均海温与官方同海域区域站点的热斑像素 SST 平均只差 **0.013 °C（r = 0.717）**，偏差量级远小于季节与年际信号；真正对不上的是绝对白化等级（DHW），原因是**基线长度**而不是海温本身 —— 详见第七节。

## 七、已经做完的验证证据（2026-10 复核，全部可当场复算）
